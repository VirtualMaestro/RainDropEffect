# Mesh capacity arithmetic existed twice and the copies had drifted

**Date:** 2026-09-10 20:05
**Files:** `Runtime/Simulation/LayerRuntimeFactory.cs`, `LayerRuntime.cs`, `StaticLayerRuntime.cs`, `SimpleLayerRuntime.cs`, `FlowLayerRuntime.cs`, `FrictionLayerRuntime.cs`, `Tests/Editor/LayerCapacityTests.cs`
**Severity:** medium

## Problem

`LayerRuntimeFactory` exposed `StaticCapacity`, `DropCapacity` and `TrailCapacity` — helpers whose
whole job was to say how large a layer's mesh must be. Nothing in the package, the host project or
the tests called any of them. Each runtime computed the same numbers again inline in its own base
constructor call.

Being unused was not the defect. Being unused **and wrong** was. `TrailCapacity` returned
`2·t·p` vertices and `6·t·(p−1)` indices; since 2.0.1 every ribbon also emits a head quad, so the
real budget is `t·(2p + 4)` and `t·(6(p−1) + 6)`. It also skipped the clamps the runtimes apply —
`Mathf.Clamp(…, 1, 32)` on the trail count and `(…, 4, 96)` on the point count — so at
`MaxCount = 0` it answered 0 where the runtime allocates for 1.

Nothing failed loudly, and that is the point: `RainBatchMesh.AddVertex` deliberately does not throw
in the frame loop. It sets `Overflowed` and hands back a scratch vertex. A caller who trusted
`TrailCapacity` would have got a mesh a head quad per trail too small and silently lost geometry.

## Root Cause

The head quad was added in 2.0.1 by editing the capacity expression **in the two runtimes that
allocate trail meshes**, because that is where the constructor argument was and where the change was
visibly needed. The factory's copy was never in the diff and never in a test, so nothing pointed at
it.

The deeper cause is that the duplication was invisible in both directions. The runtimes did not call
the factory, so a compiler could not connect them; no test compared the two answers, so a runner
could not either. The only thing linking them was that a human had once written the same formula in
two places — and the second place was dead, which is exactly the code least likely to be re-read
when the first place changes.

The clamp divergence has the same shape and is older: the runtimes grew `Mathf.Clamp` guards, the
factory copy did not.

## Solution

Made the factory the single source of truth rather than deleting the dead code.

- `MeshCapacity` — a small readonly struct so one call can return both numbers, and
  `LayerRuntime` gained a constructor overload taking it. Without that, a base-constructor call
  cannot consume a two-`out` helper and the duplication would have survived.
- The tier clamps moved into `DropCount`, `TrailCount` and `TrailPoints`. Each runtime's private
  `Cap` / `Pts` now delegates there, so the clamps exist once too.
- `TrailCapacity` folds in `TrailBuffer.HeadVertices` / `HeadIndices`, using the same constants
  `EmitRibbon` reserves against — so the emitter and the allocator cannot disagree about the head
  quad even in principle.
- All four runtimes pass `LayerRuntimeFactory.*Capacity(...)` straight into `base(...)`.

Deleting the three helpers would have been a smaller diff and would have left the arithmetic
duplicated across four constructors, with nothing stopping the next family from copying it a fifth
time.

## Prevention

- **Dead code that computes something is worse than dead code that does something.** An unused
  method still reads as documentation, and this one documented a lie. When a formula is duplicated,
  either wire the copies together or delete the spare — do not leave a second opinion lying around.
- **When a change touches an arithmetic expression, grep for the constants in it, not just the
  file.** The 2.0.1 head-quad work would have found the factory copy by grepping `2 *` and
  `6 *` over `Simulation/`, or `MaxTrails(` / `MaxPoints(`.
- **A regression test for a "silent" failure has to assert the invariant, not the symptom.** There is
  no exception and no log to catch here, so the test compares the factory's answer with
  `runtime.Mesh.VertexCapacity` / `IndexCapacity` directly, across all three quality tiers and
  including out-of-range `MaxCount` / `MaxPoints` values. That last part is what surfaced the clamp
  divergence, which was invisible at ordinary settings.
- **Friction had no full-capacity emit test** even though it shares the ribbon and the head quad with
  Flow; only Flow got one in 2.0.1. When two families share machinery, a guard on one of them is
  half a guard. Added `FrictionFullCapacityAtHighQualityDoesNotOverflow`.

## Verification

`LayerCapacityTests` failed 3 of 5 before the change (`DropCapacity`, and `TrailCapacity` for both
trail families, all first diverging at `MaxCount 0` and again on the head quad) and passes 5 of 5
after. Full suites: 108 EditMode + 49 PlayMode, zero failures, zero compiler warnings.
